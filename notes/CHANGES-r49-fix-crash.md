# r49 — ИСПРАВЛЕНИЕ ВЫЛЕТА (причина найдена в исходниках Telegram)

Сборка: **mod-12.10.3-mod-r49** (Latest) · APK 35 708 395 Б ·
sha256 `74a2700be6c4dc5ce6b25e6fe7a39ae583e921462f7c7794daca884facfdfabb`
Ничего не откатывали: все 18 пунктов r46 на месте, добавлены исправления.

## Причина вылета (одна, найдена точно)

В r48 подняли лимит аккаунтов **только в Java**: `UserConfig.MAX_ACCOUNT_COUNT = 10`.
Нативная часть Telegram осталась на своём пределе — в `TMessagesProj/jni/tgnet/Defines.h`
написано `#define MAX_ACCOUNT_COUNT 5`, а нативный
`ConnectionsManager::getInstance(int)` — это `switch` с ветками `case 0..4` и
`default`, который возвращает **тот же самый объект `instance4`**:

```cpp
case 4:
default:
    static ConnectionsManager instance4(4);
    return instance4;
```

Что дальше происходило при запуске:

1. `ApplicationLoader.postInitApplication()` (Java) идёт циклом
   `for (a = 0; a < UserConfig.MAX_ACCOUNT_COUNT; a++)` и для **каждого** аккаунта
   создаёт `ConnectionsManager.getInstance(a)`;
2. для аккаунтов 6–10 нативный код возвращал объект `instance4`;
3. Java-конструктор в конце вызывает `init(...)` → `native_init(...)` →
   `ConnectionsManager::getInstance(instanceNum).init(...)`, то есть у **одного и
   того же** нативного объекта `init()` вызывался повторно, а внутри него каждый
   раз делается `pthread_create(&networkThread, nullptr, ThreadProc, this)`,
   заново читается чужой конфиг (`loadConfig()`), пересоздаются дата-центры;
4. несколько сетевых потоков на одном объекте + перезапись `jniEnv[instanceNum]`
   и гонка за состояние соединения → падение приложения сразу после запуска.

В r45 этого не было, потому что там лимит Java (4) был **меньше** нативного (5).
Отсюда и «в r45 работало, в r48 вылетает».

## Что исправлено (без потери функционала, без откатов)

1. **Лимит синхронизирован**: `MAX_ACCOUNT_COUNT` теперь правится в одном месте
   (`KamiGramUserConfig` → скрипт `apply_r43_patches.py::native_accounts()`),
   и оттуда же уходит в нативный код:
   * `jni/tgnet/Defines.h` → `/* KAMIGRAM_NATIVE_ACCOUNTS */ #define MAX_ACCOUNT_COUNT 10`;
   * `jni/tgnet/ConnectionsManager.cpp` → добавлены ветки `case 5..8` и свой
     `default: instance9`, то есть у каждого из 10 аккаунтов **свой** нативный
     объект сети (проверено компиляцией фрагмента `g++ -std=c++17 -fsyntax-only`).
   Аккаунтов по-прежнему 10 — функциональность сохранена.
2. **Скрытие встроенных прокси больше ничего не ломает** (это был второй баг r48):
   раньше фильтр переписывал **глобальный** `SharedConfig.proxyList` — список
   оставался пустым на экране прокси, а встроенные прокси исчезали из общего
   состояния (другие потоки читают его). Теперь фильтруется только локальный
   список экрана, глобальные данные не трогаются.
3. **Убраны двойные стартовые вызовы**: обёртки аварийного режима теперь
   **заменяют** строку Telegram, а не добавляют вторую копию (в прошлой сборке
   `KamiGramTheme.apply()` и `KamiGramProxyPower.tick()` выполнялись по два раза
   на каждом старте).
4. **Аварийный режим (новое)**: `KamiGramSelfCheck` считает запуски —
   три неудачных подряд включают режим, в котором мод пропускает тяжёлые
   стартовые шаги (оформление, авто-прокси, фоновая проверка). Приложение
   гарантированно открывается, состояние видно в центре Sakura
   («Состояние: … · вход выполнен»). После успешного запуска счётчик сбрасывается.
5. **Первый запуск (новое)**: `KamiGramFirstRun` — без «мастера знакомства»,
   плюс страховка: если активный аккаунт пуст, а в другом есть вход, активным
   становится тот, где вход есть (после обновления версии пользователь не
   попадает на пустой экран входа).

## Если вылет всё же повторится

Мод теперь сам защищается: три неудачных запуска подряд включают аварийный режим,
приложение открывается, и в центре Sakura будет строка
«Состояние: аварийный режим включён». Тогда пришлите эту строку — по ней сразу
видно, что мод отключил свои тяжёлые шаги. Ничего из функций при этом не
удаляется: текст, чаты, вход, настройки работают как обычно.
